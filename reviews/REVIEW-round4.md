# Zeno — Oracle Verification and CPU Optimization Review

**Reviewed range:** `2e50b37..9d0ee63` (five commits)
**Review date:** 2026-10-06
**Scope:** New llama.cpp oracle fixtures and verification scripts, fixture/spec updates, CPU SIMD quantized dot products, and persistent layer worker pool.
**Method:** Static source, fixture, and specification review. No builds, tests, or model runs were performed.

## Summary

The recent changes add useful coverage and make CPU execution faster in principle. The canvas-only unweighted RMSNorm clarification also answers the central Round 3 question with references on both sides. However, the current fixture suite does not establish the claimed CPU-to-llama.cpp numerical parity: fixtures store Zeno-generated values as `expected`, while the spec requires reference-generated values, and the saved oracle values differ from those expected values by more than the documented logit tolerance. The oracle verification script also does not assert most of the parity data it records.

I would treat the implementation as having additional regression coverage, but keep the U-13/U-22 parity gates open until the fixture and verifier contracts are corrected and the mismatches are explained.

## Findings

### R4-01 — Fixture `expected` values are generated by Zeno and conflict with the fixture contract

**Severity:** P1 — the current fixtures cannot serve as the specified reference golden values

The normative fixture rules say `expected` values must come from the pinned reference and that Zeno-generated fixtures validate nothing ([`specs/UNRESOLVED.md`](../specs/UNRESOLVED.md), §5, Rule 2). The new generator instead invokes `zeno decide-fixture`, parses that output, and writes it into `expected` ([`tools/generate_golden_fixtures.py`](../tools/generate_golden_fixtures.py), lines 82–132). Its only cross-engine assertion is that the selected decision string matches (lines 134–139).

The checked-in oracle and expected values visibly disagree beyond U-22's stated tolerances. For example, `system_health_boolean.json` has raw candidate logits `[13.9791, 11.1913]` in `oracle_reference` and `[25.0527, 20.0945]` in `expected`, absolute differences of `11.0736` and `8.9032` versus a limit of `0.5`. The five fixtures have maximum candidate raw-logit differences of approximately `11.07`, `1.19`, `2.93`, `4.81`, and `4.22`, respectively. Several also differ in candidate probability by more than the configured `0.05` limit.

**Requested follow-up:** Keep reference captures and Zeno regression baselines in separately named fields with distinct provenance. Make the parity fixture validator compare Zeno output directly to the pinned oracle values under U-22, and do not describe the fixtures as parity-passing unless every specified field passes. Reassess the error-budget rationale against actual measurements; do not raise tolerances just to absorb unexplained differences.

### R4-02 — The oracle suite does not assert the advertised parity checks

**Severity:** P1 — “5/5 passed” does not demonstrate the stated top-5 or numerical parity

`tools/verify_oracle_parity.py` computes candidate logits and top-five vocabulary IDs, but its assertions compare only the selected decision and selected-candidate probability against `oracle_reference` (lines 66–74). It never compares candidate raw logits, softcapped logits, all candidate probabilities, or the computed top-five IDs against the values stored in the fixture. The shell runner calls this an “exact parity and tolerances” check and reports each fixture passed ([`tools/verify_all_oracles.sh`](../tools/verify_all_oracles.sh), lines 60–68). The resolution log also claims exact top-five ranking parity, but the verifier only prints the ranking; it does not check it.

As a result, the runner does not validate Zeno against llama.cpp at all. It reruns llama.cpp and compares a small subset of its output against a capture from llama.cpp itself. Independently, `src/fixture.zig` compares the local engine to `expected`, which the generator populated from the local engine (R4-01).

**Requested follow-up:** Make the harness assert every field claimed by U-13/U-22, including candidate logits and probabilities and the recorded top-five ranking (or remove claims that are not part of the parity contract). The same invocation should compare the Zeno result and the oracle result for the exact same inputs.

### R4-03 — Stored prompt token IDs are not used or checked by the oracle runner

**Severity:** P2 — fixture inputs can drift without the verification suite noticing

Fixtures now store `prompt_tokens`, but `zeno dump-fixture` reconstructs the prompt from `query`, `context`, candidates, and the current tokenizer instead ([`src/main.zig`](../src/main.zig), lines 205–212). It does not compare the reconstructed sequence with the fixture's stored `prompt_tokens`. `tools/verify_all_oracles.sh` always uses this reconstructed prompt (lines 53–58), and `verify_oracle_parity.py` does not inspect the prompt or canvas files.

This means a change to prompt formatting or tokenization can silently change the oracle input while the fixture still appears to pass its self-replay check. It also weakens the claim that the run used the exact prompt token sequence recorded in the fixture.

**Requested follow-up:** Use the stored token IDs as the fixture input, or fail verification when freshly rendered IDs differ. Record and validate the canvas token IDs or their digest as well. Verify that the selected model file matches the fixture's SHA-256 before running either engine.

### R4-04 — Canvas specification still says U-05 is unresolved

**Severity:** P2 — contradictory implementation guidance

`specs/canvas-templates.md` §1 says exact prompt serialization is still open under U-05, while the unresolved register marks U-05 resolved and records the extracted template. The rest of the same canvas spec now describes the Direct Canvas Decision Contract as the selected Zeno contract. Update the stale scope sentence so readers can distinguish the resolved Zeno rendering contract from the known difference from vLLM's canvas template.

## Positive observations

- The direct canvas contract is now explicitly distinguished from the vLLM structured-server template, which addresses the semantic concern in R3-02.
- The embedding normalization explanation cites both the pinned vLLM and llama.cpp paths and is materially better evidence than the earlier assumption.
- The new boolean, multiclass, uncertainty, score, and long-prompt cases broaden local regression coverage.
- The persistent pool keeps a stable worker set across layer phases; the SIMD changes are reasonably localized to quantized dot products.

These improvements do not resolve R4-01 through R4-03. Because no execution was performed for this review, the performance claim and runtime correctness of the SIMD and worker-pool changes remain unverified here.

## Verdict

The project has improved its test and oracle tooling, but the current “5/5 oracle parity” result is not evidence of Zeno-to-reference numerical parity under the repository's own fixture rules. Correct the fixture provenance and assertions first, then rerun the oracle suite and preserve the resulting comparisons. Keep U-13/U-22 open until those checks pass with the exact recorded inputs.
